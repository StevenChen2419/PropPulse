## Schema and ownership

`backend/app/models.py` adds `Event` using existing UUID/string and naive-UTC
timestamp conventions:

| Column | Contract |
| --- | --- |
| `id` | UUID primary key; generated by the ORM |
| `provider` | Required canonical provider identifier |
| `provider_event_id` | Required opaque provider identity; case/punctuation preserved |
| `sport_key` | Required canonical sport key |
| `home_team`, `away_team` | Required independently verified participant labels |
| `scheduled_start_at` | Required UTC schedule, stored as timestamp without timezone |
| `updated_at` | Required local UTC metadata-write time, ORM default/on-update |

There is no cancellation, postponement, prediction, provider-update timestamp,
team table, or historical competition-status schema in this phase. Local event
metadata time must never be interpreted as sportsbook observation/freshness.

`Prop.event_id` is a nullable UUID, with relationship `Prop.event` / `Event.props`.
Offers and snapshots remain related through their existing props. No duplicate
event reference is added to offers, snapshots, logs, or user selections.

Existing `Prop.odds_event_id`, `odds_sport_key`, `game_time`, `opponent`, `is_home`,
and all UUID/user relationships remain intact. No API exposes or groups by the
new relationship yet.

### Constraints and indexes

- `uq_events_provider_sport_event`: unique `(provider, sport_key, provider_event_id)`.
  Different providers/sports may use the same opaque provider ID.
- `ix_events_sport_start`: `(sport_key, scheduled_start_at)` for upcoming games
  within a sport.
- `ck_events_nonempty_identity`: nonblank provider, sport key, provider event ID.
- `ck_events_nonempty_teams`: nonblank participant labels.
- `ck_events_distinct_teams`: participants differ after trimming/case normalization.
- `ix_props_event_id`: indexed nullable prop relationship.
- `fk_props_event_id_events`: references `events.id`, `ON DELETE RESTRICT`.

The ORM relationship uses `passive_deletes="all"`: deleting an Event does not
silently null its loaded props to bypass the restrictive foreign key. Events with
linked props cannot be deleted through normal ORM or direct SQL operations.

### Domain validation and link protection

`backend/app/services/event_identity.py` provides reusable metadata validation and
an explicit linkage guard, without querying, saving, upserting, or backfilling:

- Provider/sport tokens normalize to canonical lowercase identifiers. Sport keys
  must be among currently supported provider keys.
- Provider event IDs remain opaque, unparsed, and unchanged; empty/control-character
  identities are rejected. In particular, names, teams, and times cannot generate
  a provider identity.
- Participant names are nonempty, normalized for whitespace, distinct ignoring
  case, and cannot be unknown placeholders. Shape validation does not prove
  provenance: future callers must supply independently verified provider metadata.
- External metadata timestamps require an explicit timezone and convert to naive
  UTC. Internal ORM naive datetimes explicitly mean UTC, matching existing models.
- Persisted Event provider/sport/provider-ID values are immutable through the ORM.
  Schedule corrections can retain the same Event UUID.
- `link_prop_to_event` requires an Event UUID, rejects conflicting legacy provider
  or sport identity, and rejects replacement of an existing known relationship.
  Its caller must persist/flush the validated Event first. The helper is not wired
  into ingestion in this phase.

Both direct FK assignment and relationship assignment have ORM guards against
changing or clearing known prop-event linkage. PostgreSQL additionally uses the
small `guard_prop_event_identity()` function and `trg_props_event_identity`
BEFORE UPDATE OF event_id trigger. NULL-to-known initial linkage and no-op updates
are allowed; known-to-different or known-to-NULL changes fail with SQLSTATE `23514`.
This trigger is justified by the explicit requirement to protect prop identity,
including bulk/direct SQL operations that bypass ORM validators. It does not
change existing reconciliation or offer-freshness behavior.

`create_all` alone does not install that PostgreSQL trigger. Alembic upgrade is
required for the complete database protection. SQLite tests verify ORM behavior;
real PostgreSQL tests verify FK/trigger enforcement. Administrative SQL can bypass
some domain-only canonicalization/provenance checks; future application writes
must use validated metadata and guarded linkage rather than raw inferred values.

## Migration design

New revision: `20261014_02_event_identity.py`, parent `20261014_01`.

The earlier revision is unchanged. Its empty-database adoption path imports
**current** model metadata and calls `create_all`. Consequently, a fresh migration
through revision 01 already contains the Event table/column by the time revision
02 executes. Revision 02 handles both supported paths:

1. **Complete revision-01 existing database:** frozen prerequisites verify every
   pre-3B table and required column. Events/linkage are both absent. Create the
   Event table, constraints/indexes, nullable UUID column, and restrictive FK;
   validate the result and install the known-link trigger.
2. **Fresh database/current-model bootstrap:** accept an already complete,
   compatible Event table and prop relationship, validate their definitions, and
   install the trigger. Never recreate or overwrite matching objects.

No revision history rewrite, stamp command, guessed repair, or data backfill is
used. No existing rows are updated by revision 02. All prior props remain with
NULL linkage; a newly created Event table contains zero rows.

### Compatibility safeguards

The migration refuses missing baseline tables/columns, only one of Event/linkage
existing, incompatible Event columns/types/nullability/defaults, incorrect PK or
provider uniqueness/checks, missing/wrong indexes or foreign keys, and partial or
conflicting named trigger/function definitions. Exact compatible pre-created
objects are accepted; constraints are not silently replaced or weakened.

PostgreSQL transactional DDL rolls back the revision when validation fails,
including DDL issued before a late trigger conflict. Repeated `upgrade head` is
a no-op; explicit revalidation of compatible objects preserves rows and the
existing trigger function identity. The revision intentionally requires PostgreSQL;
it does not claim SQLite DDL can prove this migration.

### Backward compatibility boundary

After the migration, existing research/ingestion works with `event_id=NULL`:
unchanged logic still reads legacy provider identity and schedule. Offer policy,
same-line comparison, timestamps, quotas, advisory locking, historical windows,
player matching, saved props, and slips were not modified.

The new mapped column means **do not start this model version on an unmigrated
development database**. Explicitly authorize/apply the migration first. Application
startup `create_all` cannot add a column to an existing table; starting it first
can create only Event and leave a partial schema, which revision 02 refuses.

Existing isolated test table lists were extended to include Event, and legacy
fixtures explicitly remove the new table/column/FK/index so old-schema tests stay
genuine. The intentionally minimal SQLite revision-01 tests target that original
revision rather than asking a partial fixture to migrate to the new head.

## Safe future upgrade procedure — not executed on development

1. Obtain explicit authorization to upgrade the intended database. Stop all
   application/refresh/manual-ingestion processes; retain disabled refresh.
2. Take and verify a recoverable backup without overwriting existing backups.
   Review the private target configuration without printing credentials.
3. Inspect `alembic current`; the previously verified development revision is
   `20261014_01`. Stop on unexpected revision/schema state; do not stamp it.
4. Review this revision and execute the explicitly targeted upgrade from backend:
   `.\venv\Scripts\python.exe -m alembic -c alembic.ini upgrade 20261014_02`.
5. Confirm the revision, expected constraints/indexes/guard, zero automatically
   created Event records, and NULL legacy links. Compare old IDs, counts, prices,
   timestamps, snapshots, and user selections with the backup/integrity manifest.
6. Only after schema verification, start the compatible application. Do not launch
   ingestion or backfill as an implicit migration verification step.

If incompatible partial objects exist, the migration refuses them. Investigate
and plan an explicit correction instead of dropping/recreating them blindly.

### Rollback limitations

Automatic downgrade raises an error, preserving event identities, relationships,
constraints, and guards. Application rollback should revert code while retaining
the additive schema and revision marker. Older code can leave the nullable field
untouched. Clearing/reassigning known links or physically removing schema requires
a separately reviewed correction/migration and preservation plan. Restoring an
old backup can lose later user data and is never an automatic rollback action.
